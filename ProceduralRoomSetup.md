# Procedural Room Generator

Open **Tools > Procedural Rooms > Room Generator** after Unity finishes importing the scripts.

## First room

1. Click **New Profile** and choose an asset location. The profile includes a saved invisible navigation tile and references the supplied **NotWalkableTile** for boundary collision. Profiles created from the Assets Create menu need **Create Utility Tiles** once.
2. Select a handmade room prefab, such as RoomSmall1, and click **Use Selected Room**. Check **Source Ground Map** and choose the base-elevation ground map when necessary. Alternatively, assign that Tilemap directly.
3. Click **Import Palettes**. This copies tile asset references, observed variant frequencies, the ground material, and sorting settings. It does not modify the source room. A visible wall tilemap can be assigned separately; do not use an invisible collision map as a visual wall palette.
4. Review **Generation Profile**. Under **Room Plane**, set **Elevation Level** and **Base Z** independently (both default to 0). Keep terrain tiles in Ground Tiles; move border/corner artwork to the optional edge rules. Wall visuals are optional; the physical boundary is generated independently even when Wall Tiles is empty. Assign the four flat trapdoor tiles under **Floor Trapdoor**, or disable **Include Floor Gateway**.
5. Click **Preview Layout**, then **Create Editable Room**. Green cells are ground, gray cells are candidate north-side visual walls, dark outlines are invisible boundaries, yellow is player spawn, and bright blue marks gateways and trapdoors. Orange cells mark the optional secret branch. The cached bitmap shows logical boundaries. With **Fade Obscuring Walls** enabled, wall columns are retained and fade near the player in Play Mode; with it disabled, the builder omits obstructing columns instead.
6. Edit the created room's Tilemaps and markers with Unity's usual tools. Click **Validate Edited Room**, then **Bake New Prefab**. Add the saved prefab to the corresponding small/medium/large/XL pool on RoomManager.

Creating another room never replaces an existing scene room. Scene creation supports Undo. Bake always chooses a new asset path, including when an existing filename is entered. **Edited Room** can be reassigned to another generated scene room after reopening the window.

## Layout and grid

- All eight shapes use a local seeded random source, not Unity's gameplay random state. The original Rectangle, Chambers, Organic, and Cavern values remain unchanged for saved-profile compatibility. Four additional choices are **Donut**, **Hallway Caves**, **Twin Donuts**, and **Winding Passage**.
- **Donut** creates a circular/elliptical ring with a protected central hole. **Twin Donuts** joins two rings with two protected holes. **Hallway Caves** creates a mostly linear passage with gently changing width and bends; **Winding Passage** uses a stronger winding course. Passage centerlines advance along X instead of random chamber/corridor networks, avoiding arbitrary self-crossings; short approaches connect the configured exits. Width/Height control the overall bounds; Corridor Half Width controls passage/ring thickness. Very small rings have smaller holes so navigation and trapdoors still fit. Approaches and a connecting navigation route remain reserved against props.
- **Cavern** uses cellular noise and smoothing for irregular cave edges, broad pockets, and internal voids instead of the Organic shape's circular chambers and straight cross-corridors. **Cavern Floor Fill** controls initial floor density (0.4-0.7); higher values usually produce broader floors. **Cavern Smoothing Passes** (1-6) smooths jagged edges and removes small pockets. Start with 0.58 and four passes. Disconnected floor islands are removed; curved, reserved approaches connect enabled gateways to a central clearing with room for a trapdoor. Small dimensions or low density can produce mostly tunnels. Cavern settings appear only when Cavern is selected; Chamber Count does not apply.
- All outputs use an independent Grid matching the dungeon: Isometric Z As Y, XYZ swizzle, cell size `(0.32, 0.16, 2)`, no cell gap, unit scale, and no rotation. This makes scene previews and baked rooms independent of their temporary editor parent.
- Dimensions and spacing are in cells, not world units. The root Grid is retained when RoomManager instantiates the prefab under its existing hierarchy.
- Generation supports one flat section per regular or secret room at any nonnegative **Elevation Level** and **Base Z**. Elevation Level sets navigation, player/enemy markers, gateways/destinations, tilemap visibility/sorting, wall fading, and light visibility; it does not add a physical offset. Base Z is the actual starting tile-cell Z for ground, navigation, collision, trapdoors, and secret maps. It moves markers, props, and lights by the matching native Grid displacement and rebuilds boundary geometry. For Elevation Level 5, Base Z 5, and wall height 3, ground/navigation/collision use cell Z 5 and walls use 5, 6, 7. Setting level 5 with Base Z 0 is also valid. Both editable creation and seed batches use the saved profile values; the bitmap preview remains a logical X/Y layout. Automatic stairs and terraces remain absent; existing handmade rooms are unaffected.
- **Surface Height In Tiles** defaults to one cell height (`0.16` world units). Cube ground visuals stay at their original anchor; flat navigation, collision, props, lights, and markers are positioned on the raised top surface. Walls start at the same visual base as ground on north-side boundaries, not at the raised navigation surface. The surface offset is a transform offset, not Grid cell Z: the Grid Z size of `2` is not used to raise navigation. Adjust the surface height when your cube sprite pivots/PPU put their top at a different height.
- Every ground cell, including the perimeter, is initially walkable. Decoration footprints can remove occupied cells, but room connectivity is preserved. DetectableTiles stays empty for later manual stair authoring. Both navigation map types receive their existing AStar gizmo scripts; enable Gizmos in the Scene view. Old Navigation Inset settings are no longer used.
- Corridor Half Width reserves broad routes for the spawn, directional gateways, and safe landing markers. This is not a character-collider measurement; verify clearance in Play Mode.
- GroundLevel0, WallVisuals0, WalkableTiles0, DetectableTiles, and ColliderLevel0 derive from the same terrain. Invisible maps use disabled renderers. Visible wall cubes are placed only outside north-east/north-west boundaries; south-west/south-east boundaries have no wall visuals, but still have collision.
- Boundary collision uses **NotWalkableTile** on **ColliderLevel0**, with a TilemapCollider2D, static Rigidbody2D, and synchronously updated CompositeCollider2D. Paint or erase tiles at the configured Base Z with the Tile Palette; Unity updates collision automatically, without a generator rebuild button or hand-built PolygonCollider2D paths. The supplied sprite's physics bounds are centered using the TilemapCollider2D offset, preserving its authored beveled outline and shared asset unchanged. The collision map's renderer remains hidden; its tiles are still editable. Old profiles containing sprite-less collision utility tiles fall back to the supplied asset when generating new rooms. Gateway triggers and the secret entrance blocker keep their own authored/generated shapes; they are not boundary tilemaps.
- No ElevationLevel tilemap is necessary. The original manually authored ramp, elevation-trigger, and single-link A* behavior is retained. Automatic-stair runtime changes, including multi-link routing, have been reverted.

## Visual rules and population

Ground edge rules match the exact cardinal mask of **missing ground neighbors**. Wall edge rules match the exact mask of **adjacent ground neighbors**. NorthEast is cell `+X`, NorthWest `+Y`, SouthWest `-X`, and SouthEast `-Y`. Combined sides identify corners. Unmatched masks use the weighted fallback pool. Unity RuleTile assets are supported as TileBase entries; their own neighbor rules are evaluated on the output map.

Palette import does not infer artwork semantics or copy hand-painted per-cell rotations, colors, or transforms. Review imported tiles before building. It also does not copy authored room lighting: add suitable lights manually or provide light prefabs, especially when using a lit URP material.

**Forward Direction** and **Backward Direction** choose the actual side where each directional gateway is placed. Choose distinct sides for forward/backward. NorthEast is the `+X` boundary, NorthWest `+Y`, SouthWest `-X`, and SouthEast `-Y`. Floor trapdoors do not use directions.

**Forward Collider Size** and **Backward Collider Size** are independent `(width along edge, depth across edge)` values in grid cells. These generate isometric parallelogram PolygonCollider2D triggers aligned to the selected edge. Width is limited to the reserved corridor (twice Corridor Half Width); depth supports `0.25-4` cells. Destination landings are placed sufficiently far inward to avoid gateway triggers. ForwardDestination follows the backward entrance; BackwardDestination follows the forward exit. Direction metadata matches the side where each landing actually sits. RoomManager retains its opposite-direction compatibility rule: the next room's backward entrance must face opposite the previous forward exit. For a pool containing only this profile, choose opposite forward/backward directions; otherwise include appropriately matching profiles in the pool.

Assign separate **North East Gateway Visual Prefab** and **North West Gateway Visual Prefab** for their respective wall faces. Each must be visual-only, without Gateway components or colliders; a single SpriteRenderer visual is recommended. The prefab's root pivot is placed halfway between the gateway floor cell and its outward wall cell, on their shared wall contact rather than at the trigger center. Arrange the artwork inside the prefab relative to that contact pivot; the generator does not rotate one face to impersonate the other. The hidden old Gateway Visual Prefab field is retained as a fallback for existing profiles until directional prefabs are assigned. Southern directional gateways still get a Light2D with configurable color, intensity, and radius, or the optional **South Gateway Light Prefab** (one Light2D, no sprites/colliders/Gateway components). GatewayVisibility disables/fades that light together with locking its trigger. Custom light prefabs retain their authored light settings. Trapdoors use their own tilemap instead of these visuals or lights.

## Floor trapdoors

Enable **Include Floor Gateway** in a regular-room profile and assign **Trapdoor North East**, **North West**, **South East**, and **South West** to saved flat TileBase assets. These are the four quadrants of a 2x2 tile patch in grid coordinates:

```text
cell +Y:   NW  NE
origin:    SW  SE
		   +X ->
```

The isometric Grid projects this patch into a diamond. The seeded generator chooses a random interior location with a one-cell clearance ring, away from directional triggers and landing markers. The footprint is reserved against decoration and enemy placement. **FloorTrapdoorTiles** sits on the flat cube-top surface above the ordinary ground, so hiding it leaves normal ground beneath it. Its PolygonCollider2D trigger covers exactly 2x2 grid cells, not a 2x2 world-unit rectangle.

GatewayFloorVisibility starts the trapdoor hidden and unusable. RoomManager chooses one floor gateway and reveals/enables it when the floor is cleared. Direction is ignored; the old Floor Direction and Floor Collider Size controls are removed. Existing profiles need the new tile references assigned before rebuilding. Existing baked prefabs are not changed.

## Secret entrances

In a regular-room profile, enable **Include Secret Gateway**. Choose **Secret Direction** on a side unused by regular exits. Its flow is always **SecretForward**. **Secret Collider Size** uses the same directional width/depth units. **Secret Path Length** supports 6-48 cells, and **Secret Path Half Width** supports 2-12 cells. New profiles default to a 16-cell-long, 11-cell-wide hidden section, rather than a tiny entrance patch. Existing profiles retain their saved length; increase it to enlarge their hidden section.

The generator adds a reserved branch, **SecretPathGround**, **SecretPathWalls**, a full-width solid **SecretEntranceBlocker**, and the SecretBackward return destination. Secret ground is removed from GroundLevel0 and placed exclusively in its revealable map: hiding it does not leave visible terrain underneath. GatewaySecretVisibility hides the branch and gateway while locked, keeps the entrance blocker enabled across all lanes, and shows a closed wall on northern entrances. Unlocking reveals the entire path, removes that blocker/closed wall, and enables the gateway trigger and its visual or southern light. Wall-height layers follow the same unlock state. All parts remain visible/editable during authoring; the locked state is applied at runtime.

RoomManager still selects one entrance according to its existing chance and compatible secret prefab pool. Its key room is chosen from the entrance room and later regular rooms only. Clearing that key room triggers the existing unlock prompt and opens the entrance. No new key item or separate progression system is added. The branch's navigation is baked; the solid blocker controls access while locked. No generated enemies or decorations are placed in that branch.

## Generating secret rooms

Enable **Is Secret Room** in the profile. The inspector shows **Secret Room Backward Direction** and its collider size instead of regular forward/backward controls. The generated room contains exactly one **SecretBackward gateway**, plus one **SecretForward arrival destination** safely inward from that gateway. There is no SecretForward gateway inside the secret room. Floor trapdoors and extra locked secret entrances are suppressed regardless of their toggles.

Bake these prefabs into **RoomManager > Secret Room Prefabs**, not the regular size pools. **Secret Room Backward Direction** must face opposite the regular room's **Secret Direction**. For example, a NorthWest SecretForward entrance pairs with a secret room whose backward direction is SouthEast. The generated regular room includes its SecretBackward return destination.

RoomManager connects the regular SecretForward entrance to the secret room's SecretForward destination, and connects its sole SecretBackward gateway back to the regular room. Its existing key-room selection and unlock prompt are unchanged. Secret-room population behavior is retained: GenerateSecretRoom does not register passive enemy markers with the regular floor spawner.

## Manual stairs and room composition

Generate, validate, and bake the flat rooms first. Author stairs, ramp colliders, AStarStairLink anchors, detectable stair tiles, and RampElevationTrigger components manually in the base room. The flat generator does not construct stairs. Existing generated stair objects or old baked prefabs are not automatically deleted or rewritten.

Open **Tools > Procedural Rooms > Room Composer**:

1. Assign **Base Room** and **Attached Room** to two separate room roots, either scene instances or prefab assets. Scene instances are easiest for assigning child objects and editing boundaries. Each source needs one connected flat AStarWalkableMap on its configured base-Z plane, unit root scale, no root rotation, and a compatible Grid ancestor. The base root must own its only RoomInstance.
2. Assign the base room's authored **Stair Link**. **Entry Anchor** (lower landing) and **Exit Anchor** (upper landing) are optional overrides; assigned anchors must belong to the base hierarchy. When empty, the Composer resolves the existing AStarStairLink fallback from the shared **RampMovementTrigger collider and Ramp Forward direction**, and saves endpoint markers only in the new output. It does not derive endpoints from the top/bottom elevation-trigger colliders. Assign separate **Lower Elevation Trigger** and **Upper Elevation Trigger** components from the base hierarchy, each covering its resolved landing. Keep the movement trigger, detectable stair tiles, and side protection authored manually. If automatic points fall outside walkable floor or elevation triggers, adjust the ramp shape/direction, or supply explicit anchors.
3. Assign **Attached Landing Anchor**, a Transform inside the attached room on walkable tiles. It can be an empty landing marker or an existing spawn/destination helper. Choose **Upper End (Ascend)** or **Lower End (Descend)**, then set **Attached Tilemap Level** explicitly. It must be higher than the base for ascent or lower for descent, and nonnegative. Levels need not be adjacent: one authored stair can connect gameplay levels 0 and 5. Set **Attached Base Z** independently: a value of 5 puts the attached ground, navigation, and collision cells at Z 5, with wall columns continuing at 5, 6, 7, etc. The base room's cells are unchanged.
4. Manually open the solid boundaries along the stair connection. Set **Gateway Seed**, or click **New Seed** to choose a new gateway arrangement. Click **Create Combined Room**. This clones both sources and translates the attached landing exactly to the chosen stair endpoint; it never rotates geometry or guesses from room bounds. The final physical height follows your authored stairs, not an additional automatic rise. Both landing-clearance and centerline collision checks produce named Console warnings rather than blocking composition or baking. Missing navigation or central ramp-trigger/detection coverage still prevents creation. Collision warnings do not prove physical traversal works; verify your stairs in Play Mode.
5. Review the new hierarchy, click **Validate Combined Room**, then **Bake New Combined Prefab**. The composer has its own validation/baking buttons; the flat generator's validator is not for combined rooms. Each bake chooses a unique asset path. Add the resulting prefab to one appropriate RoomManager pool entry, not two.

The output has an empty RoomInstance parent, BaseGeometry, and ElevationSection_N children with compatible Grids. Original rooms remain unchanged; creation is a single Undo action. Do not leave the original scene instances active alongside the output when testing gameplay, since their collision and markers still exist.

Only the base owns progression through the combined root's RoomInstance settings and player spawn. Regular forward/backward exits are selected from both sections using **Gateway Seed**, with distinct sides and one gateway per flow. Each selected gateway retains the corresponding opposite-flow arrival destination on the same side and in the same section. Gateways and destinations receive that section's gameplay level, so a retained attached destination at level 5 is serialized as level 5. Runtime gateway destination links are cleared for RoomManager to reconnect. One floor gateway/trapdoor is also selected from either section when present. Unselected gateways, arrival markers and trapdoor artwork are removed. The attached copy loses its player spawn and duplicate RoomInstance; geometry, navigation, decorations, lights, and enemy markers remain. Locked secret progression stays with the base; attached sections with a locked secret entrance remain unsupported. RoomManager's inter-room opposite-direction compatibility requirements are unchanged.

The section's navigation, tilemap visibility/sorting, wall fading, light visibility, elevation groups, enemy markers, enemy elevations, and any elevation-trigger metadata are shifted by the difference between its source and target gameplay level. The selected lower/upper triggers are set to the matching combined navigation levels. Base metadata otherwise remains authored as-is. For a descending composition, configure the base room's navigation and related markers/visibility consistently at its higher level before composing. Existing visibility thresholds still apply: if levels 0 and 5 should both remain visible, increase the relevant **TilemapElevationVisibility > Disable Threshold** above that difference, or disable threshold hiding.

Base Z changes occupied cell coordinates, not just a Transform's Z value. Tile references, per-cell colors, transforms, flags, and relative wall layers are preserved; TilemapCollider2D collision follows the changed cells. Markers, props, and lights move consistently with the shifted tiles, then the entire attached section is translated so its landing still exactly matches the authored stair endpoint. This alignment means Base Z is not an extra physical rise added on top of your stairs. Add/adjust the stair endpoints to control the actual connection height.

The Composer configures generated **ColliderLevel** maps for automatic tile collision after final alignment and keeps their TilemapCollider2D/CompositeCollider2D enabled. On these collision maps it disables **TilemapElevationVisibility > Affect Colliders**, so visual elevation fading cannot remove a section's physical boundary. Ordinary, uncomposed maps retain their previous collider-visibility behavior. Both sections' 2D collision can therefore still obstruct each other where they overlap; review named warnings and fix actual obstruction rather than relying on world Z to separate collision. Existing scene rooms and baked assets are not rewritten automatically; regenerate rooms to adopt the supplied boundary tiles.

Shifted maps receive **ProceduralTilemapPlane**, whose Base Z identifies the navigation plane for 2D world-to-cell queries. Keep that value matched to the flat navigation cells when editing the room. Ground/navigation/collision use one plane per section; visible walls may use additional Z layers. Authored detectable stair tiles may occupy several palette Z positions. Room Generator validation/baking supports uncomposed single-section rooms at their configured elevation and base Z; use Room Composer validation/baking for combined rooms.

This version supports two flat sections through **one authored stair link**, using the existing runtime's single-link A*, including nonadjacent gameplay levels. Multi-stair chains and arbitrary overlapping floors are not supported. Validation checks connected navigation, both walkable landings, central trigger/detection coverage, elevation triggers, and player/enemy/destination marker levels. All landing/centerline solid-collision checks are advisory and identify colliders in Console warnings. Verify the full stair width, side rails, character clearance, camera depth, collision layers, lighting, and floor-generation room spacing in Play Mode. **Tools > Procedural Rooms > Run Composer Checks** runs focused composition, fading and population regressions, including 0-to-5 transitions, base cell Z 5, collider preservation, seeded gateway pairs, automatic endpoints, and advisory collisions.

No Grid removal is required. If a scene source already inherits the dungeon Grid, the clone receives its own compatible Grid so the new prefab is self-contained. Keep Isometric Z As Y/XYZ `(0.32, 0.16, 2)`. The combined root has no Grid component; its children supply the Grids needed by Tilemaps.

## Wall height

**Wall Height In Tiles** supports 1-8. Each wall column is painted at `(x, y, z)` with Z from **Base Z** to **Base Z + height - 1**, in the existing WallVisuals0, SecretPathWalls, or SecretEntranceClosedWall map. There are no separate `_Height` maps. Choose that Tilemap and change the Tile Palette's Z position to edit a particular layer. Existing map names keep their `0` suffix for compatibility; it does not override the configured plane.

Wall bases use exactly the ground Tilemap's local position and tile anchor `(0.5, 0.5, 0)`, with the same orientation, material, Individual renderer mode, sorting layer, and sorting order. There is no cube-top or half-Z wall transform offset. Ground sorting settings control both maps; legacy wall-only sorting fields are retained for serialized compatibility but no longer used. Secret-path walls and the closed secret entrance wall use this same base placement.

On this project's exact Grid, Unity's native conversion makes **Z + 1 raise world Y by 0.16** and also increase world Z by 2. A height of 3 therefore gives layers at +0, +0.16, and +0.32 relative to ground's visual base. **Wall tile-anchor Z stays zero.** Retain the compatible Grid and sufficient camera depth range.

**Fade Obscuring Walls** defaults on. Each regular/secret-path wall map gets **WallOcclusionFade**, also added when composing existing generated rooms. It groups cells by their X/Y wall column, projects each column's sprite bounds into world XY, and fades the entire column when the player is inside or near that area. **Wall Fade Padding** expands the area in world units (default 0.24); **Wall Faded Alpha** defaults to 0.15; **Wall Fade Duration** defaults to 0.2 seconds. Walls restore their original cell colors when the player leaves. Walls on the player's level or above can fade; lower sections do not fade for a player above them. Configure the component directly on manually authored wall Tilemaps if needed.

Fading modifies per-cell color only: it does not move walls, disable collision, remove navigation, or overwrite the whole Tilemap's alpha. Elevation/secret visibility continues to multiply the result. The closed, locked secret-door cover is not proximity-faded. Cached sprite bounds are conservative and can fade a little more than the opaque artwork; custom shader deformation is not modeled. Verify the effect with the actual player, camera, and material in Play Mode.

With **Fade Obscuring Walls** disabled, the builder retains the previous static mesh filter: transformed sprite triangles are tested against ground-cell diamonds, including hidden secret ground and every wall layer. With matching Individual renderers and the global custom transparency axis, wall tiles sorted behind ground are allowed to overlap it. Other intersections omit the entire column, never walkable tiles. RuleTile variants and AnimatedTile frames are considered. Full-rectangle sprite meshes may conservatively exclude transparent areas. Camera-specific sorting overrides are not modeled.

The physical boundary remains flat and independent of wall art. Southern edges still have no visible walls. All Z layers in secret maps inherit their existing reveal/hide state without extra references.

## Authoring details

Enemy Spawn Point Prefab is optional and must contain exactly one EnemySpawnPoint. Generated markers use the profile's **Elevation Level** and have autonomous spawning disabled; the existing scene EnemySpawnerManager remains responsible for spawning. Without a template, each marker requests one enemy at its own location.

**Enemy Boundary Clearance** defaults to three cells (range 1-8). Enemy markers require a fully walkable neighborhood of that radius, keeping them away from outer boundaries, ring holes, and cut decoration footprints. Marker prefabs with a nonzero Spawn Radius receive additional conservative clearance in world units. Narrow passages can fit fewer markers than requested; the generator warns instead of placing unsafe markers. Verify the largest enemy collider and its actual spawn scatter in Play Mode, and increase clearance as needed.

Decoration Prefabs may contain pots, props, and lighting. Their combined renderer and solid-collider bounds plus Decoration Clearance must fit outside the reserved routes. By default, placement removes the occupied footprint from navigation and rejects disconnected results. For decorations that must not cut navigation, add **ProceduralDecorationSettings** to the decoration prefab's root and turn off **Cuts Walkable Tiles**. They still obey footprint, route and prop-spacing checks, but do not remove walkable or detectable cells. This toggle does not disable the prefab's solid colliders: remove them or use triggers for genuinely pass-through decoration. Oversized props may not fit. Fewer props/markers than requested produces a warning, not an invalid room. Cut footprints remain excluded after a breakable prop disappears.

Under **Scattered Lights**, assign saved prefabs to **Light Prefabs**, set **Light Count**, and choose **Light Spacing** in cells. Lights are seeded across unreserved walkable ground without cutting navigation. Each prefab must contain Light2D components and no solid colliders, RoomInstance, Gateway, or EnemySpawnPoint components. Sprite meshes/trigger colliders are permitted; light color, intensity and radius remain authored. The generator adds/sets LightElevationVisibility at the profile's **Elevation Level**; composition shifts attached lights to the selected gameplay level and relocates them with the section's base-Z cells. Lights are independent of Decoration Count and southern gateway lights. Authored room lighting is not imported automatically.

When manually expanding GroundLevel0, update ColliderLevel0 and WalkableTiles0 too. Paint/erase **NotWalkableTile** on ColliderLevel0 at its Base Z; the TilemapCollider2D updates automatically during Unity's normal tilemap update. Then validate and bake before adding manual stairs or levels. Validation checks flat connectivity, complete boundary coverage, marker placement, the Grid, north-facing wall footprints and sprite obstruction, gizmos, and gateway/destination compatibility. It does not infer terrain or stair geometry from edits. Regeneration creates a new room rather than merging with manual edits. Previously baked rooms are not rewritten.

## Batches and checks

**Bake Seed Batch** writes 1-32 new prefabs using consecutive seeds beginning at the profile seed. Choose an existing folder under Assets. This does not add scene objects or update RoomManager pools. If a batch fails, earlier successfully saved prefabs remain and the error reports how many were saved.

**Run Generator Checks** runs focused population and room-plane regressions, plus four new shapes across seeds and sizes, protected ring holes, direction-specific wall visuals, inland enemy markers including template spawn radius, supplied collision tiles, and live paint/erase geometry updates. Plane checks cover independent elevation/base Z 0/5 combinations for regular and secret rooms, wall layering, shifted markers/props/lights, boundary geometry, elevation metadata, flat-Z actor navigation projection, prefab round-trips, and negative input rejection. All these checks also run in the full suite.

**Tools > Procedural Rooms > Run Checks** uses temporary assets and an isolated preview scene, plus a temporary ordinary additive scene for editor Undo checks. It checks 384 seeded flat layouts across eight shapes, 128 cavern fill/smoothing/dimension/entrance cases, 12 regular gateway combinations, exact trapdoor coverage, all four secret directions for both Rectangle and Cavern with a sole backward return, enlarged hidden ground and full-width blocker, actual manager key unlock and return linking, and gizmos. Wall builds cover heights 1/4/8 across all shapes, ground-aligned wall placement/rendering, native Z spacing, static sprite obstruction filtering, proximity fading, unchanged navigation/collision, secret visibility, and serialized Z cells. The current RoomGenerationProfile is additionally tested on clones without modifying its asset. Composition checks cover 0-to-5 levels/base Z 5, retained collider geometry through visibility changes, seeded gateway/arrival pairs and floor trapdoors from both sections, matching destination elevation, optional collider-derived stair endpoints, advisory landing/centerline warnings, one progression owner, source and tile-state preservation, metadata shifting, original single-stair A* both ways, prefab persistence, inherited Grids, Undo, and invalid-input rejection. Population checks verify decoration cut opt-outs, ordinary cutting props, and deterministic scattered lights with spacing and unchanged navigation. Bitmap previews, prefab non-overwrite, and unchanged Unity random state are also checked. **Run Composer Checks** runs the focused composition, fade, and population checks; **Run Preview Checks** separately checks authored-room selection and basic bitmap pixels. Results are written to `Temp/ProceduralRoomChecks.result`; the full suite also exports `Temp/ProceduralRoomCavernPreview.png`. Exit Play Mode first.

After baking, verify character clearance, enemy spawning, gateway transitions, floor exit unlocking, materials, and lighting in Play Mode before adding a large batch to production pools.
